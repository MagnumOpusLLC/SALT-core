# Precomputed compliant KV versus fresh policy context

**Measured verdict:** The same fictional policy and five concise questions behaved differently by platform. The authenticated **925-row cached parent** beat a fresh in-request policy context on **c6i CPU**, but did **not** reduce five-turn HTTP wall on **Mac Metal**, and saved only a small HTTP margin on **V520 ROCm** that disappeared when parent import was included. This directly tests the concern that carrying a longer live KV can impose recurring continuation cost that offsets avoided policy PREFILL. The native phase buckets establish the tradeoff; they do **not** by themselves locate that cost specifically in attention arithmetic, page faults, GPU synchronization, or expert readiness.

## Mechanism boundary and intended four-choice workload

The tested mechanism is **preservation, authenticated import, and continuation of one complete curatable policy/model state**. A later request starts from that state. It is **not** a vLLM/SGLang-style prefix-cache lookup or hit, and it is **not** a DPR parent-exact transition hit that skips inference. None of those cache-hit mechanisms was measured here. Decode speed and the long-KV continuation toll remain active engineering work.

The intended domain workload is different from both completed tests: incorporate a specific policy/system prompt and fixed four-option decision rule into the parent, then send a structured domain input **without supplying the policy or answer-bearing candidate text** and have decode return only the selected code (or a short answer). The fresh comparator must submit that same policy/system/context to PREFILL before deciding. The earlier [Exp 3](../exp3-multiple-select/README.md) put the answers in the choices and scored 20/20 without parent KV; the present comparison used concise **free-form** replies, not a fixed four-code selector. Neither establishes speed or parent-dependent accuracy for that intended structured-output cell. No production codebook or policy document was supplied or compiled by this report.

## Why the wall differs

Each platform processed **247 new input / 288 output tokens** in the cached-parent session, versus **612 / 296** in the fresh-policy session. The first fresh request alone processed **411 new input tokens** versus **46** for parent; the subsequent question texts were the same, but each arm had a different retained KV history. Native PREFILL and decode phase totals reconcile with HTTP wall; “other” is the small in-request remainder. The phase buckets are whole parent walls, not pure arithmetic timers.

| Host | First parent / fresh HTTP s | First parent / fresh PREFILL s | Five-turn parent / fresh PREFILL s | Five-turn parent / fresh decode s | Parent / fresh decode ms/output |
|---|---:|---:|---:|---:|---:|
| Mac Metal | 17.560 / 23.124 | 4.101 / 11.132 | 17.812 / 22.296 | **56.221 / 50.925** | 195.211 / 172.045 |
| c6i CPU | 34.106 / 104.969 | 10.937 / 82.964 | 59.392 / 128.670 | **101.047 / 96.230** | 350.859 / 325.101 |
| V520 ROCm | 31.536 / 46.901 | 4.283 / 22.856 | 19.931 / 36.862 | **120.000 / 107.578** | 416.665 / 363.441 |

On **Mac**, avoiding 365 input tokens saved **4.483 s PREFILL**, but the parent arm spent **5.295 s more decode** despite generating **eight fewer outputs**; the result is **0.823 s slower** HTTP wall. On **V520**, a **16.931 s** PREFILL saving was mostly offset by **12.421 s** additional decode, leaving just **4.090 s** HTTP savings. On **c6i**, the **69.278 s** PREFILL saving dominated **4.817 s** additional decode, leaving **64.305 s** HTTP savings. These are realized platform workshapes, not evidence that stateful inference is intrinsically fast or slow. In particular, a longer loaded KV correlates with higher measured decode ms/output here, but source-level attribution to attention versus backend waits/resource actions remains open.

## Semantics, exactness, and limits

- All **30 HTTP responses** returned 200 and stopped naturally. Within each arm, Mac Metal, c6i CPU, and V520 ROCm produced identical prompt IDs, output IDs, full text, finish reasons, final positions, complete-state SHA, facts SHA, payload SHA, and canonical bytes. The cached arm ended at position **1460** with state SHA `39feba2ed8acdb09bdfd4d1ef379f84e258848e0d9697f9783aac84b241bf5dd`; the fresh arm ended at position **908** with state SHA `ea364e3f671f786918cd71fdc398634d77f19e4d923d149a2f3a08244b9bc8cc`. These two distinct histories are **not** compared byte-for-byte to each other.
- Full-text manual review: cached-parent responses meet the source-bounded behavior/facts in **2.1, 2.2, 2.3, and 2.5**. For **2.4**, the model refused the user's contradictory fact rewrite and retained cobalt/slot 41, but did **not explicitly restate the record's rejection of network saturation**; grade **PARTIAL** against the full rubric. Fresh-policy responses meet all five, including explicit rejection of saturation in **2.4**. No response claims that rollback or drain was executed. Neither arm's rubric result should be upgraded from tokens or state hashes alone.
- The parent includes **two prior natural model responses** as well as policy text; fresh receives raw policy text once. The representations, active positions, and completion lengths differ. No no-policy/no-parent short-answer control, repeated host-state samples, phase-aligned GPU duty/power, device-fault census, or exact attention/resource/synchronization decomposition was run. RSS is all-inclusive sampled OS resident; it is **not** device VRAM or a sum of per-request memory.

**Conclusion:** Precomputing the policy **works as an exact, portable state transition**, but it is **not a universal latency win** at this state length. On c6i it saves substantial request wall; on Mac the continuation toll exceeds the avoided fresh-policy PREFILL, and on V520 import overhead erases a small request-wall gain. This is the measured issue to diagnose before claiming that “decode merely surfaces a precomputed concept” at lower total cost. The six detailed local/remote receipts are under ignored `logs/experiments/policy-context-v1/`; no rollback or runtime optimization was attempted.
